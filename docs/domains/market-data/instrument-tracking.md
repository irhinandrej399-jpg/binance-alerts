# Управление отслеживаемыми инструментами

## Границы и контракт

Market Data получает желаемое состояние инструмента из Kafka и хранит его в своей БД.
Alerts остаётся владельцем пользовательских правил; здесь нет пользователей, порогов
или подсчёта подписчиков. Alerts должен публиковать новую версию при первом/последнем
активном правиле, атомарно со своими изменениями через собственный outbox.
Alerts пока не реализован: этот документ и JSON Schema задают контракт для будущего производителя.

Топик: `market.instrument-tracking.v1`, ключ — UTF-8 symbol (например BTCUSDT).
[JSON Schema](../../../contracts/events/instrument-tracking.v1.schema.json).

```json
{"schema_version":1,"event_type":"InstrumentTrackingChanged","symbol":"BTCUSDT","enabled":true,"version":1}
```

Версия — положительное int64, строго возрастает для каждой пары у единственного
логического владельца Alerts. Это версия желания, не количество подписчиков и не время.
При disabled запись сохраняется: удаление tombstone позволило бы старому enabled
повторно включить инструмент. Новое включение после disabled требует большей версии.

## Правила и сценарии

| ID | Вход / состояние | Ожидаемое поведение |
|---|---|---|
| TR-01 | Первая enabled=true/false | Сохранить состояние и версию |
| TR-02 | Повтор той же версии и состояния | Успех без изменения |
| TR-03 | Более старая версия | Игнорировать без отката состояния |
| TR-04 | Большая версия с новым состоянием | Применить |
| TR-05 | Та же версия, другое состояние | ErrVersionConflict, состояние сохранить |
| TR-06 | Нет обязательного поля, неверный тип/ключ/версия/schema/type | ErrInvalidCommand без записи |
| TR-07 | Ошибка БД или отмена | Ошибка наружу; Kafka offset не подтверждается |
| TR-08 | Перезапуск | Восстановить активный список из PostgreSQL |
| TR-09 | Невалидная/конфликтующая команда | Сохранить отказ по topic/partition/offset, затем разрешить mark offset |
| TR-10 | Сбой сохранения отказа | Повторять, не пропускать команду |

Лишние поля допускаются для совместимого расширения. Symbol проверяется синтаксически
`[A-Z0-9]+`; факт существования пары подтверждает Binance, а не этот обработчик.
Целое `version` не должно проходить через float. Null не заменяет false/0.

## Kafka consumer

Одна группа `market-data.tracking.v1` работает с одной долговечной БД Market Data.
Начальная позиция для новой группы — oldest. Offset отмечается только после commit
состояния или долговечного отказа. Автокоммит может произойти позже — это допускает
повтор, который безопасен благодаря версиям. При временной ошибке повторяется то же
сообщение, следующая команда этой партиции не обгоняет его. При отмене/rebalance
незавершённая команда не подтверждается. Отказы содержат координаты и причину,
но не исходный payload. Принятые состояния и отказы не очищаются автоматически.

Потеря БД вместе с сохранёнными Kafka offsets не восстанавливается автоматически:
нужен replay с начала доступного журнала либо отдельный snapshot. Пока retention
команд не обеспечивает полный replay, snapshot/API — отдельная будущая задача.

## Применение к Binance

Для совместимости `TRACKING_MODE=static` остаётся значением по умолчанию (SYMBOLS).
В `dynamic` единственный источник набора — таблица instrument_tracking; SYMBOLS
не используется как скрытый дополнительный список.

Супервизор раз в TRACKING_REFRESH_INTERVAL читает активный набор, сравнивает как множество
и заменяет сессию только при изменении. Старый reader отменяется и завершается до запуска
нового; после перезапуска процесса набор повторно читается из БД. Пустой набор — штатный idle, без соединения
с Binance. При недоступной БД действующий reader сохраняется, readiness становится false.
После восстановления чтения состояния готовность снова зависит от reader или idle.

В первой реализации замена набора выполняется переподключением с повторным SUBSCRIBE.
Это создаёт окно потери сделок и может затронуть уже отслеживаемые пары. Обновления
сгруппированы периодом опроса. Incremental SUBSCRIBE/UNSUBSCRIBE без замены сессии и backfill
не входят в этот шаг. Более 1024 пар не помещаются в одну сессию: новый набор отклоняется
с ошибкой, действующая сессия сохраняется, readiness=false. Шардинг соединений — отдельная задача.
Готовность потока не является подтверждением активации отдельного пользовательского правила.

## Проверки

Unit: валидация, сохранение контекста/ошибок, обработка consumer offsets, supervisor
на управляемых каналах снимков без sleep. PostgreSQL integration: версии, tombstone,
конкурентные команды, восстановление списка и долговечный отказ. Kafka integration:
реальная команда → consumer → БД и восстановление после остановки consumer.
Изменение WebSocket-набора проверяется локальным источником, не нагрузкой на Binance.
